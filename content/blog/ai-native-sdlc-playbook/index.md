## （一）编写代码不再是瓶颈

{{< lead >}}

各企业一年以前已经开始以难以想象的速度使用AI去编写代码，但围绕代码建立的配套工作流程却没能跟上这一步伐。

{{< /lead >}}

许多工程团队依然沿用着旧有的审批关卡、代码审查、交接流程和管理政策，这使得借助Claude Code等Agent级编程解决方案所带来生产力提升大打折扣。

软件开发生命周期（software development lifecycle，SDLC）是将软件从创意转化为落地产品的完整流程。大多数企业采用的流程大同小异，基本都包含规划、设计、构建、测试、部署和运维这六个阶段。传统模式下，每个阶段都是由不同角色主导的独立环节：产品经理撰写需求，技术架构师将需求转化为设计方案，工程师进行代码的编写构建，合规企业的质量保障（Quality Assurance，QA）团队负责验证，发布团队负责上线，而运维团队则监控运行状态。工作任务通过文档、工单和签字确认在不同的环节流转。

传统的SDLC流程繁琐，旨在每个环节都权责明确、可控可追溯。然后，传统SDLC诞生的背景，是编写与实现代码尚属最耗时、最昂贵阶段的时代，它的设计本是为了在该环境下最大化提升效率——但如今情况已然改变。无论是产品需求文档（Product Requirement Documents，PRD）、工时预估仪式，还是产品安全审查，它们存在的初衷，都是为了长达数周、数月乃至数季度的开发过程中强制保持团队对齐。

传统的SDLC的控件和管控机制还有一个特点，那就是默认每一步都由人工完成。而那些创造出高价值的企业，已经围绕现代Agentic级AI的新能力重构了流程，同时确保人类依然参与把关。在本指南中，我们将结合我们应用AI团队在内部将Claude深度融入SDLC各个阶段的最佳实践，分享如何加速开发并提升整体流程效率——这些经验均源自于我们与客户的真实合作。

当编写代码不再是瓶颈，且构建阶段的运转速度超出了传统SDLC所能支持的极限时，会出现三个必然现象：

+ 瓶颈转移到了构建阶段的左右两侧，这主要体现在规划、审查以及部署环节，而这些环节依然在以人工速度运行。
+ 管控机制开始与现实脱节，并变得难以驾驭。当代码由人类编写时，手动逐行审查是有意义的；但一旦大部分代码变更都由Agent编写，这种做法就再也跟不上节奏了。
+ 治理成本不讲反升，因为例外情况已然需要通过每周或者每月才召开一次的会议与委员会进行流转审批。

{{< sdlc-figure kind="bottleneck" anchor="figure-1" label="图 1" title="瓶颈已转移" caption="构建不再是瓶颈——围绕着它的那些“人工速度”环节才是。当构建阶段压缩至几小时甚至几分钟时，这些环节的耗时却依然如故。" >}}

以安全环节的瓶颈为例：安全团队的人力配置是基于“人类产出速度”设定的。因此，当Agent成倍增加代码产量时，要么安全审查队列发生严重的积压，要么未经充分审查的代码被直接上线。受监管的合规企业无法接受这两种结果中的任何一种，因此其安全与策略检查机制必须跟上Agent的速度。

为了更好地释放Agent级AI带来的生产力红利并保障其安全性，传统的SDLC必须经历一场与代码实现阶段同等深度的全面变革。

{{< lead >}}

什么是AI原生的SDLC？

{{< /lead >}}

AI原生的sdlc是一种被重塑的开发流程，它将传统的管控目标与全新的执行手段相结合。整个流程不再是单向的线性流转，而是演变为一个闭环，且AI被深度嵌入到每一个环节之中。AI原生的SDLC致力于推动自动化的交接与下一阶段动作的自动触发，从而解决了传统SDLC各阶段之间以来人工交接、效率低下且笨拙的问题。

转变

{{< /lead >}}

下表展示了在Claude的支持下，传统的SDLC和AI原生SDLC两者之间的极端差异。大多数企业实际上处于这两列之间某个位置。

| 阶段                     | 传统 SDLC                                                    | AI 原生 SDLC                                                 |
| :----------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **规划**<br>*(Plan)*     | 需求由委员会收集，通过研讨会与签字审批进行提炼，最后由人工撰写。 | Claude 直接从源头综合梳理痛点，并写入 `intent.md` 文件中，既便于人类阅读，又可供机器直接执行。 |
| **设计**<br>*(Design)*   | 规格说明书由分析师撰写，再由设计师进行解析。                 | 需求与设计被压缩至与 Agent 的单次会话中完成；全程由编码为技能（skills）的规范指导，并在 Git 中进行版本控制。 |
| **构建**<br>*(Build)*    | 测试与代码均为手动编写，文档则在主开发完成后补写。           | 测试与代码由 AI 生成；组织知识以具备版本控制、机器可读的 `CLAUDE.md` 文件与技能（skills）形式维护。 |
| **测试**<br>*(Test)*     | 在阶段边界设立 QA 审批卡点。                                 | 将持续评估（evals）无缝贯穿于整个代码实现过程中。            |
| **部署**<br>*(Deploy)*   | 人工审查每行代码；治理发生在周期性审查中且缺乏一致性。       | 采用多层 Agent 审查，人工审查仅留给强监管与关键代码。治理在 AI 操作时实时生效，利用钩子（hooks）卡点。 |
| **维护**<br>*(Maintain)* | 由人工监控线上生产环境的 Bug。                               | Agent 实时监控线上部署。任何突破控制带的异常都会被诊断，并作为新 `intent.md` 重新写入闭环。 |

贯穿右侧一栏的核心主线是被提交的产物。每个阶段均以向版本控制系统中写入一个产物作为结束（包括intent.md、spec.md、plan.md、代码变更及其测试用例、带有审查结果的PR，以及故障记录），而下一阶段则通过读取该产物来开启。在前期阶段.md文件是最主要的产物，因为产品负责人和Agent都能读取并基于同一个文件采取行动。从构建阶段开始，产物则转变为代码及其相关记录。这一连串的提交记录同时也构成了审计追踪链：谁提出了什么需求，Agent生成了什么内容，以及谁批准了该操作。

人类依然对每一个需要主观判断的决策承担责任。在Agent驱动的SDLC世界里，人类的注意力会随着那些被审查的产物一同发生转移。

## （二）实战剧本

{{< lead >}}

这些实战剧本是本指南的核心，分为六个非线性的阶段（规划、设计、构建、测试、部署、维护），共同覆盖了软件的完整周期。

{{< /lead >}}

每个剧本均包含以下内容：

+ 核心变化：改变了什么；
+ 快速入门：如何开始；
+ 实施步骤：具体的落实步骤；
+ 治理考量：合规与管控要点；
+ 效果评估：如何衡量是否生效。

这些步骤具备高度模块化的特点，企业可以根据自身的独特需求，选择在不同阶段优先推进不同环节的转型。每个剧本都会在“前置条件”下列出其依赖项，并在后续的依赖关系图中进行详细展现。

一个阶段的结束以提交产物为标志，该记录会随之触发下一个阶段。例如：一份被通过的intent.md会触发需求与设计环节，一份被批准的spec.md会触发规划模式，合并后的PR会触发流水线，而生产环境中突破控制带的异常则会撰写下一份的intent.md——如此往复，形成持续运转的闭环。

起初，你需要人工提示词来驱动每一个步骤，而终极目标是建立一个自动化闭环：在此闭环中，每一个被通过的产物都会自动触发下一个质量卡点。人类的注意力由此集中在各个卡点上，只需审查Agent标识出的重点，而无需从头去启动每一个阶段。

{{< sdlc-figure kind="dependencies" anchor="figure-3" label="图 3" title="实战剧本依赖关系图" caption="各列按阶段分组，箭头表示引入剧本的先后关系，而非软件开发的固定执行顺序。可从任一橙色起点开始；实线是前置依赖，虚线仅表示有帮助。" >}}

## （三）阶段一：规划

构想不再需要等待专人去整理撰写。需求意图只需以发起者的原话记录一次，即可作为受版本控制的产物，直接供下一阶段读取并执行。

### 捕获为intend.md

{{< lead >}}

作为开启软件开发流程的起点，intend.md意图文件可以通过多种渠道生成：有人产生了一个新构想、提交了一张工单，或是系统通过告警暴露了一个线上故障（参见阶段6：维护）

{{< /lead >}}

当有人产生构想时，他们会与Claude进行头脑风暴，生成一份markdown格式的雏形规格说明。而在传统的SDLC中，这个人必须先去说服产品团队的成员，让他们配合自己或者代为将这个构想整理成正式文档。

有Claude生成的雏形规格说明不仅具备良好的可读性、受版本控制，还能立即供下一阶段直接调用。这份雏形规格说明会被保存为Intent.md。

无论意图是源自事件触发还是Agent自动生成，其处理流程都一致：在提交之前，产品负责人会审查并纠正由Agent撰写的intent.md。

**快速入门**

{{< info-list >}}

前置条件

: 无

基础设施

: 为非工程人员提供Claude的访问权限；一套约定好的intent.md模版；一个产品负责人能够关注的、共享且版本控制的意图储存位置。对于单一产品而言，最简单的存放方式是在该产品的代码仓库中建立一个intent/文件夹。这种配置可以将“产物链”与由此衍生出的代码紧密放在一起。只有当意图跨越多个仓库时，设立独立的意图仓库才值得付出额外的维护成本；而在单体大仓库中，它仅仅是一个目录。阶段3：构建的侧边栏将详细说明该存储位置如何与已包含相关记录的Jira或需求管理工具进行关联。

{{< /info-list >}}

搭建这一环境是平台团队或工程团队的一次任务。考虑到贡献者来自组织中的各个部门，技术团队成员需要搭建好意图的存储位置，并明确谁拥有写入权限。

一旦仓库建立完成，缺乏 Git 经验的贡献者无需直接使用 Git。相反，通过连接器连接至版本控制系统（如Github），Claude即可代表他们在claude.ai或Corework中代为提交Markdown文件。

**如何执行**

1. 发起者用自己的语言向Claude描述问题。发起者可以描述他们目前无法做到什么、该构想会影响到谁、理想的效果是怎样的，或者哪些内容属于超出范围。无需使用任何正式或规范的术语。
2. 进行头脑风暴直到构想变得具体。Claude会像需求分析师一样提出问题：涉及范围、目标用户、限制条件以及成功标准等。
3. 让Claude使用组织统一的模版将结果撰写为intent.md。该模版可以由技术团队成员预先配置并由Team Lead批准编码为一项“技能(skill)”。这可以涵盖问题背景、预期成果、受影响的用户和系统、约束条件以及开放性问题。
4. 发起者对Claude理解有偏差的地方进行纠正。
5. 将intent.md提交至共享存储位置。作者信息与时间戳将自动加入记录中，随后产品负责人便可以从该位置接手并推进构想。

**样式示例**

```text
# 意图：理赔状态自助查询
作者：J.Ortiz（理赔运营部）。状态：草稿。


## 问题背景
客户频繁打电话给客服中心询问理赔进度。理赔处理人员大约三分之一的通话时间都花费在仅涉及状态查询的电话上。

## 预期成果
客户可以在自助门户网站中直接查看理赔状态、下一步流程以及预计完成日期。

## 受影响的用户和系统
理赔处理人员、门户网站团队、核心理赔API

## 约束条件
门户网站会话中不得引入新的个人身份信息（PII）。仅允许使用现有的身份验证机制。

## 待确认问题
第三方公估人是否也需要访问权限
```

**治理考量**

治理凭证是已提交的intent.md，其中列出了作者、时间戳以及完整的修改历史。这些信息都会记录在意图存储位置的Git提交历史中。由产品负责人进行审批，而决定将意图推进至阶段2：设计的“通过”或“拒绝”决策，会通过代码合并或关闭评审的形式记录下来。

**效果评估**

{{< info-list >}}

先行指标

: 从首次对话到提交intent.md所消耗的时间，该时间可以从记录了作者与时间戳的Git历史中读取。预期是将原本长达数周的需求挖掘与精炼周期，缩短至数小时级别。

滞后指标

: 存活率，即产品负责人接受并推进至阶段2：设计而非直接关闭的intent.md文件占比。通过或拒绝的决策将记录为产物的合并或评审的关闭。此外，还包括在同一变更的首个spec.md提交之后，对intent.md所做出的修改的次数。

{{< /info-list >}}

## （四）阶段二：设计

需求梳理与架构设计缩减合并为同一个环节。合规与技术策略在撰写规格说明spec.md的同时便已经生效，而不是在数周后的评审中才被折腾发现。

### 需求与设计

{{< lead >}}

一旦获得产品负责人的批准，Claude就会读取通过的intent.md意图文件，并生成一份需求与设计规格说明spec.md。这一过程受组织在品牌、安全、合规以及用户体验方面所沉淀的“技能”（skills）指导。

{{< /lead >}}

产品负责人对该规格说明进行评审，但是无需亲手撰写。此流程的目标是生成一份工程团队可据此制定计划的规格说明，并清晰标记出需要关注的潜在风险区域。

前端开发是最直观的示例。一旦intent.md被接受，产品负责人即可根据intent.md在Claude Design（测试版）中构建原型，对原型进行打磨，随后将其导出至Claude Code中进行构建。

**快速入门**

{{< info-list >}}

前置条件

: 编写一份intent.md文件，并将品牌、安全、合规及UX策略固化撰写为“技能（skills）”

基础设施

: 一位拥有Claude访问权限的产品负责人。无需具备工程技术背景技能。

{{< /info-list >}}

**如何执行**

1. 产品负责人开启对话，加载组织可用的各项“技能”，并附上intent.md意图文件。
2. 产品负责人的提示词只想intent.md，明确约束条件，并要求自动标记出需要关注的风险点。起初可通过人工手动运行，随后可将其固化为组织级别的斜杠命令（slash command）。在此基础上，可将意图存储位置中对intent.md的通过动作设为触发器：一旦合并即触发非交互式任务，加载组织技能运行流程，并将生成的规格说明spec.md作为Pull Request提交（阶段5: 部署中的CI/CD剧本涵盖了底层的管道搭建）。从此刻起，产品负责人的首次参与即是对该PR的评审。
3. 同一位产品负责人对照原始构想审查该规格说明spec.md。审查重点在于：该规格说明spec.md是否解决了阐明的问题？意图文件intent.md中提出的未解决的（开放）问题是已得到解答，还是被延续保留到了后续步骤？
4. 优先处理标记的风险点因为这些正是需求分析师原本会向上升级上报的问题。在工程团队看到规格说明spec.md之前，产品负责人需与各策略负责人共同解决其中的每一个风险点。
5. 将spec.md与intent.md一同提交。这对文件共同完整记录了“当时提出了什么需求”以及“最终做出了什么决策”。
6. 产品负责人决定该规格说明与意图是否可以推进至构建阶段；对于组织归类为高风险的任何内容，都需要咨询技术负责人的意见。这一最终决策始终由人类团队成员做出，而接受该规格说明正式启动**阶段三：构建**中规划模式剧本的标志。

**提示词示例**

```text
读取附件中的intent.md，并生成一份用于将其集成至我们现有代码库的需求与设计规格说明。
请应用你可用技能skills，确保该方案符合我们的品牌指南、安全策略及UX标准。将规格说明完整撰写为spec.md，以便随时交付给工程团队。
请清晰描述所有需要关注的风险区域，特别是你无法同时满足相互对立的策略要求的环节。
```



**治理考量**

最新的组织策略是在编写规格说明spec.md的同时被直接读取并应用的，而不是在数周后的评审中才被无意发现的。组织的各项技能"skills"将作为约束条件应用到规格说明中。规格说明本身、用来生成它的提示词以及当时生效的技能skills版本，都会完整记录在版本控制系统中。产品负责人终审签署规格说明，并将自动标记出的风险点分发给指定的策略责任人进行处理。

**效果评估**

{{< info-list >}}

先行指标

: 同一个变更中，从intent.md提交到spec.md提交所耗费的时间（通过比较两个Git时间戳获取），并将其与传统的“需求+设计”周期进行对比

滞后指标

: 构建开始的需求返工率。通过统计在同一变更的首个plan.md提交之后，spec.md的后续提交次数来衡量。Git日志可以直接提供这一数据。

{{< /info-list >}}

## （五）阶段三：构建

在没有通过一份构建计划plan.md之前，绝不进行任何代码实现。机构经验或组织知识被沉淀为Agent能够读取的文件，而质量与安全护栏则作为自动化代码运行，不再依赖个人的工作习惯。

### 将Claude Code的规划模式作为默认起点

{{< lead >}}

工程师在规划模式下开启Claude Code对话，向Claude提供来自**阶段2：设计**中已批准的spec.md。随后让Claude对其进行访谈式提问，不断迭代优化构建计划，直到工程师满意为止。

{{< /lead >}}

<div style="display: flex; gap: 16px; margin-top: 1rem;">
  <div style="flex: 1; background: #f5f5f5; padding: 16px; border-radius: 8px;">
    <strong>传统模式</strong>
    <p style="font-size: 14px; margin-top: 8px;">工程师阅读设计文档，然后直接开始编写代码。具体如何做出改动——细化到需要修改哪些文件、编写哪些测试——全都停留在工程师的脑海中，充其量记录在工单评论里。其他人无法对其进行审查。评审人看到的第一个东西就是最终的代码diff，此时如果发现问题，返工过程会非常缓慢。</p>
  </div>
  <div style="flex: 1; background: #fff0eb; padding: 16px; border-radius: 8px;">
    <strong>AI 原生模式</strong>
    <p style="font-size: 14px; margin-top: 8px;">工作始于一份由Claude在规划模式下生成的书面计划，在此模式下，它会读取代码库单不会做出任何修改。在编写任何代码之前，工程师会对计划进行纠偏，批准后的版本将作为plan.md提交，以供后续阶段进行核对。</p>
  </div>

**快速入门**

{{< info-list >}}

前置条件

: 意图产物（若存在intent.md或spec.md），此外CLAUDE.md文件也有助于此过程

基础设施

: 拥有代码库访问权限的Claude Code。

{{< /info-list >}}

**如何执行**

1. 工程师在规划模型下启动与Claude的对话。
2. 工程师向Claude提供intent.md与spec.md，要求生成一份实现计划，明确指出需要修改的文件、工作执行的顺序，以及用于验证的测试用例。
3. 通过询问以下问题对计划进行审视质询：该变更可能会破坏什么？哪一步风险最高？以及Claude放弃了哪些备选方案？
4. 持续迭代计划，直到一位从未参与过此前对话的工程师，仅凭这份计划就能独立完成代码变更。
5. 将批准后的计划作为plan.md提交。该计划将纳入审计追踪链，而**阶段五：部署**中的PR审查剧本会根据该计划来核对最终的代码diff。
6. 接受该计划并交由Claude执行实现。有了扎实的计划，具体代码实现通常能够一次性通过。
7. 当实际实现偏离了原计划时，必须在同一个Commit中更新plan.md。可考虑使用Git Hook来强制保持二者之间的同步。

**样式示例（plan.md）**

```text
# 计划：理赔状态自助查询（源自 2026-06-02 的 intent.md）

## 需变更的文件
portal/src/claims/StatusPanel.tsx (新建), claims-api/routes/status.py,
claims-api/tests/test_status.py

## 工作执行顺序
1. 在现有的身份验证机制后添加状态查询 API 端点 (endpoint) 。
2. 基于该 API 端点对接开发面板组件。
3. 接入门户网站的导航栏中

## 潜在风险
核心理赔 API 限制速率为 50 rps（每秒请求数）；
面板组件必须实现缓存。

## 验证依据
test_status.py 覆盖了四种理赔状态；
前端截屏与已批准的设计原型保持一致。
```

**治理考量**

设计评审发生在生成任何代码之前，此时调整路线仅仅是修改一份文档的事儿。规划模式本身强制执行了这一约束，因为在工程师接受计划之前，Claude无法对任何代码文件进行修改。该计划及其后续修订，连同批准人的信息，都会被完整记录。常规变更由工程师批准，而组织归类为更高风险的任何内容，则需要提交给技术负责人或架构师审查。

**效果评估**

{{< info-list >}}

先行指标

: 首次实现即一次性通过并合并的变更占比，以及从计划获得批准到PR合并的时间间隔（这两项数据均可以从PR元数据中读取）。

滞后指标

: 单次变更的返工循环次数（同样从PR元数据中提取），以及最终合并的代码diff与已提交的plan.md保持一致的频率。

{{< /info-list >}}

Claude Code的自动模式

{{< /lead >}}

Claude Code同样可以在自动模式下运行。在此模式下，工程师只需批准构建计划，一旦满意并完成迭代，Claude就会应用各项代码改动，而无需在每次编辑时都进行提示确认。随着后续剧本中的质量与安全护栏逐步成熟（如经过调优的CLAUDE.md、编码了组织策略的技能skills、拦截不安全操作的Hook钩子，以及Claude可自行运行的测试套件），“自动接受”将成为日常常规工作的默认选择：即拥有严谨的spec.md、较小的爆炸半径，以及已由测试充分覆盖的代码。

这种转变意味着：人类不再需要盯着Agent执行每一次修改和审查具体动作，而是转向在更长的自主运行会话结束后直接评审产物。当与Git worktrees（工作树）结合使用时，自动接受模式能进一步实现个人及团队层面的并行开发，这也是自主运行SDLC并在**阶段六：维护**中实现闭环的基础。



{{< sidebar label="侧栏" 

title="旧系统与唯一事实来源" 

note="适用于流程产生的每一种产物。"

>}}

现有的SDLC可能已经在跟踪各种产物，只是它们并非以Markdown文件的形式保存。工作事项可能存储在Jira中，需求可能存放在具备合规追溯能力的工具里，设计稿可能位于Figma，而变更审批则可能由变更委员会负责。这些系统难以被取代，因为审计人员和监管机构已经认可它们，其他团队依赖它们。因此，AI-SDLC必须适应现有的系统，并围绕它们进行设计。

在向AI-SDLC转型时，对于流程产生的每一种产物，都应指定一个系统作为唯一事实来源，其他系统则只保留该产物的副本或指向原始内容的链接。下面介绍的几种配置方式都可以确保每一种产物只有一个事实来源，但具体选择哪个系统作为事实来源，可以根据产物类型而有所不同。

**以代码库作为事实来源**。Markdown产物作为权威记录，旧系统则引用具体提交中的文件。对于由工程团队主导的组织来说，这可能是最简洁的配置方式之一，因为所有记录都集中在同一个工具中，并由统一的时间戳机制进行管理。

**以旧系统作为事实来源**。Jira、ServiceNow或需求管理工具保存权威记录，而Markdown产物则作为工作副本。Claude会在会话开始时读取权威记录，并在生成规格说明spec.md或者计划plan.md的同一次会话中，通过MCP连接器将处理结果写回旧系统。

**将建立关联作为最低要求**。所有产物都应注明其对应的记录ID，所有旧系统记录也应包含Markdown文件对应的Git提交哈希值。在向AI原生的SDLC转型时，先建立这种双向关联是一个很好的起点，但这也意味着需要暂时接受两个事实来源并存的状态。

旧系统与Markdown优先的系统可以并存，前提是两者之间建立了关联，或者明确指定其中一个系统作为唯一事实来源。

{{< /sidebar >}}



{{< lead >}}

CLAUDE.md文件

{{< /lead >}}

CLAUDE.md为Claude提供新成员加入项目时所需的背景信息，其中包括项目约定、常用命令、系统架构，以及团队最常遇到的错误。

过去只存在于团队成员头脑中或Wiki里的知识，现在会被整理成一个文件。Claude会在每次会话开始时读取该文件；整个团队共同维护它，并在出现错误时持续修改和完善。

**快速入门**

{{< info-list >}}

前置条件

: 无。

如何实施

: 一个代码仓库、已安装Claude Code，以及一位熟悉该代码库的工程师。

{{< /info-list >}}

**如何实施**

1. 在代码库中运行/init。Claude会根据它在仓库中发现的内容，生成一份初始的CLAUDE.md文件。
2. 精简生成的文件，只保留新成员入职第一天真正需要了解的内容，应保留构建、测试和代码检查的命令，重要的项目约定，以及Claude经常出错的事项。
3. 将CLAUDE.md提交到代码仓库根目录的Git版本控制中，使整个团队共享同一版本，并让其修改像代码一样接受审查。
4. 可以采用这样一条工作规则：当Claude将同一个错误犯了两次，就把相应的纠正方法写入CLAUDE.md。
5. 将文件控制在一页以内。Claude会在每次会话开始时读取全部内容；任何没有实际作用的信息都会无谓占用上下文空间。

**ClAUDE.md的示例内容**

```text
# 支付服务

## 命令

- 构建：make build
- 测试：make test（单元测试），make itest（集成测试，需要docker）
- 代码检查：make lint（在CI中运行；推送代码前先修复问题）

## 开发约定

- 使用Java 21和Spring Boot 3，禁止引入新的Lombok。
- 金额始终使用BigDecimal，绝不能使用double。
- 每个接口都必须在src/itest中包含对应的集成测试。

## 系统架构

- api存放REST控制器，这些版本由平台团队统一管理
	adapters负责与外部系统通信。
- Kafka事件定义在schemas中；不要修改自动生成的类。

## Claude 容易出错的地方
- 不要自行升级依赖版本，这些版本由平台团队统一管理。
- 旧版v1/包已被冻结；所有的修改都应在v2/中完成。
```

**治理考量**

CLAUDE.md受到版本控制，因此Claude所遵循的指令可以被审查和审计。团队规范通过该文件统一实施；对文件的所有修改都会记录在Git历史中，并由代码负责人在Pull Request（PR）审查过程中批准。

**效果评估**

{{< info-list >}}

先行指标

: Claude重复犯下那些本应被CLAUDE.md组织的错误的频率。对CLAUDE.md所做的纠正或修改，应当能够在Git历史记录中被追踪。

滞后指标

: 根据Pull Request（PR）历史记录，统计新团队成员从加入团队到第一个PR被合并所花费的时间。

{{< /info-list >}}

{{< lead >}}

将技能（Skills）作为组织知识

{{< /lead >}}

技能（Skills）是组织将其内部知识转化为可执行能力的一种方式。技能中的指令是明确的、受到版本控制的，可以广泛应用，并且能够在策略变化时进行集中更新。经验法则是：对于必须始终一致执行的组织知识，应将其编写为技能；而那些只属于CLAUDE.md或提示词的内容，则不应编写成技能。

**开始之前**

{{< info-list >}}

前置条件

: 没有硬性要求。拥有一份CLAUDE.md会有所帮助，因为它可以将智能体的工作知识保存在代码仓库中；不过，技能并不依赖它。

基础设施

: 需要一份明确指定负责人的策略，以及一份书面形式的权威信息来源。

{{< /info-list >}}

**如何实施**

1. 选择一项目前执行不一致的知识。这可以是安全标准、API设计规范或品牌规则。
2. 将其编写成一个技能。技能表现为一个包含SKILL.md的文件夹：文件的front matter（前置元数据）用于说明技能合适出发，正文则说明触发后应当执行什么。工程师根据策略负责人的权威内容编写技能，并借助Claude完成相关工作。
3. 将技能放入代码仓库的.claude/skills/<name>/目录中，使其随代码一起交付；也可以通过插件在整个组织范围内分发。
4. 测试技能能否正确触发。以不同的方式要求Claude执行相关任务，并确认技能每次都能够正确加载。
5. 当策略发生变化时，更新对应技能，并由策略负责人审核和批准此次修改。
6. 工程师会在下一次会话中自动使用新版本的技能。

**示例效果（.claude/skills/secure-api-review/SKILL.md）**

```text
---
name: secure-api-review
description: 应用API安全标准。创建或修改面向外部的借口、审查API代码或生成OpenAPI规范时使用。
---

# API安全审查
创建或修改API接口:
1. 身份验证：除/health之外，每个接口都必须使用网关JWT；不允许存在匿名访问的路由。
2. 输入验证：根据OpenAPI Scema验证请求体，并拒绝其中未定义的字段。
3. 审计：每个会改变系统状态的接口都必须生成一条审计时间，其中应包含操作者、执行动作、操作对象和时间戳。
4. 数据分类：Schema中标记pii（personally identifiable information，个人身份信息）的字段绝不能出现在日志或错误消息中。

运行script/check-endpoints.sh，并将它的输出结果包含在总结中。
```

**治理考量**

Skill是一种控制机制，不过它属于建议性控制。它能够提高Claude在编写代码时应用相关策略的可能性，但无法强制每次会话都必须遵守该策略。对于必须始终执行的策略，需要在Skill之外配合使用具有确定性的机制，例如阻止违规操作的Hook，或在Pull Request阶段重新检查策略的审查流程。Skill可以让违规情况变得少见，而Hook则可以让违规行为几乎无法发生。Skill的调用情况会记录在会话追踪信息中，并且策略负责人应像审查代码一样，审查对Skill所做的修改。

**效果评估**

{{< info-list >}}

先行指标

: 从策略负责人批准策略变更，到更新后的Skill合并完成所花费的时间。这个数据可以从Skill文件夹对应的Pull Request中获取。

滞后指标

: Pull Request审查中引用该策略的问题数量。当Skill能够在代码编写期间正确应用策略后，这一数字应该逐渐接近零。如果问题数量没有趋于零，通常意味着Skill没有被正确触发，或者Skill的具体内容已经偏离了正式策略。

{{< /info-list >}}

{{< lead >}}

将Hook作为构建阶段的防护机制

{{< /lead >}}

Skill是一种建议性的控制手段，而Hook（钩子）则是其背后的确定性执行层。Claude在实现阶段的大多数操作都是编辑文件和执行Shell命令，因此，构建阶段是Hook最适合、也最经常触发的环节。

构建阶段的Hook可以：

+ 阻止修改受保护的路径，例如自动生成的类或已经冻结的软件包；
+ 在文件被修改后自动运行格式化工具和代码检查工具，防止代码逐渐偏离规范；
+ 防止凭据等敏感信息出现在代码差异中。

对于任何必须毫无例外地执行的策略，都应当在对应Skill之外再增加Hook作为保障。Hook会对每一个符合其条件的操作执行，因此构建阶段的Hook应当运行迅速，并且只检查本次发生变化的文件。完整的测试套件等较为耗时的检查，更适合安排在提交代码时或Pull Request阶段执行。

需要人工批准的Hook应放在**阶段5：部署**的关卡中。这是因为，如果在构建阶段的每一次操作中都要求人工批准，就会让人工重新成为所有并行会话的关键路径，从而拖慢整个开发流程。

{{< lead >}}

并行会话与子智能体

{{< /lead >}}

一名工程师可以同时推进多条工作流。

并行会话是另一个完整、独立的Claude Code实例，它在自己的Git工作树中处理一项单独的任务。各个独立会话彼此之间并不了解对方的工作内容，负责协调这些会话的工程师是它们之间唯一的联系纽带。

子智能体运行在单个会话内部，是一个职责范围明确的辅助角色。它拥有自己独立的上下文窗口和工具权限，适合处理会在多项任务中反复出现的工作，例如验证应用程序是否能够按照预期执行。

并行会话可以增加工程师同时推进的任务数量，而子智能体则让每个会话专注于自身的任务。工程师的职责是协调并审查所有这些工作。

<div style="display: flex; gap: 16px; margin-top: 1rem;">
  <div style="flex: 1; background: #f5f5f5; padding: 16px; border-radius: 8px;">
    <strong>传统模式</strong>
    <p style="font-size: 14px; margin-top: 8px;">一名工程师每次只处理一项任务，并将一天甚至一周中的大量时间花在构建、测试和等待审查上。虽然可以在等待期间切换到其他任务，但上下文切换非常消耗精力，因此真正这样做的人不多。</p>
  </div>
  <div style="flex: 1; background: #fff0eb; padding: 16px; border-radius: 8px;">
    <strong>AI 原生模式</strong>
    <p style="font-size: 14px; margin-top: 8px;">一名工程师同时运行多个Claude会话，每个会话都在自己的工作树中处理各自的任务。重复性的工作则交给拥有独立上下文和工具限制的子智能体。工程师的职责会逐渐转变为编排这些工作，并最终负责建立和监控各种工作闭环。</p>
  </div>
</div>

**开始之前**

{{< info-list >}}

前置条件

: 需要一份CLAUDE.md，因为所有会话都会读取这个文件。反馈闭环（阶段4：测试）在这里也很有帮助，如果会话能够自行验证工作成果，工程师需要投入的监督就会更少。

基础设施

: 需要一个Git代码仓库，因为任务之间的隔离依赖Git工作树。还需要提前配置好权限，确保各个会话在执行被阻止认定为安全的命令时，不必等待人工批准。

{{< /info-list >}}

**如何实施**

1. 工程师将工作拆分成会修改不同文件的多个任务，并利用规划模式流程（阶段3：构建）形成的计划，判断哪些工作彼此独立。必须修改相同文件的任务应当放在同一个会话中，一个接一个地完成。
2. 为每个并行任务分配独立的工作树。例如，在一个终端中运行claude --worktree feature-auth，在另一个终端中运行claude --worktree fix-rate-limit。工作树是独立分支上的单独检出副本，可以防止不同会话在修改同一个文件时相互冲突。
3. 可以先从两个或三个并行对话开始。实际能够并行运行多少个会话，取决于一个人能够认真审查多少条工作流。因此，只有在审查工作仍然能够跟上进度的情况下，才应继续增加会话数量。
4. 将重复性的工作转化为子智能体。子智能体通过.claude/agents/目录中的Markdown文件进行定义。每个文件应包含子智能体的名称、适合在什么情况下使用它和允许它使用哪些工具。例如：代码简化子智能体负责在主Agent完成工作后，移除不必要的复杂代码；验证子智能体负责运行应用程序并检查它的行为是否符合预期；研究子智能体探索代码库并汇报调查结果，同时避免大量信息占用主会话的上下文。应当将这些子智能体的定义文件提交到Git中，这样整个团队都可以共享和使用它们。

**示例效果（.claude/agents/verifier.md）**

```markdown
---
name: verifier
description: 运行应用程序并检查修改是否生效，然后会话才能报告任务已经完成
tools: Bash, Read
---

使用make run启动应用程序。测试本次修改的功能，以及与其最接近的两个相关流程。报告你执行了什么操作、观察到了什么结果，以及任何不符合plan.md的行为。不要修复任何问题，只负责报告。 
```

**治理考虑**

更多会话意味着会产生更多工作成果，因此相应的控制措施必须来自代码仓库中的配置。仓库中的Hook和权限设置会应用于所有会话；每个会话执行的操作都会被记录下来，并归属到启动该会话的工程师名下。

{{< info-list >}}

先行指标

: 在代码审查质量能够得到保证的前提下，每名工程师同时运行的会话数量（该指标可以从OpenTelemetry导出的数据中统计）以及工程师一天中用于引导和协调会话、而不是等待任务完成的时间占比。

滞后指标

: 根据PR历史记录，综合观察每名工程师每周成功合并的变更数量及其返工率。

{{< /info-list >}}

## （六）阶段四：测试

每个会话都要先自行检查工作成果，再交由人工查看；用于引导智能体工作的配置，也要像它所编写的代码一样接受回归测试。

### 为Claude建立反馈闭环

{{< lead >}}

始终为Claude提供一种验证自身工作的方法，无论是运行测试、执行构建还是比较截图差异。会话会先检查自己的工作并修正错误，再将结果交由工程师查看。

{{< /lead >}}

不要将反馈闭环与验证子智能体（阶段3：构建）混为一谈。反馈闭环贯穿整个任务，并根据工作需要反复运行。验证子智能体则是在会话认为工作已经完成后，通过一个全新的上下文窗口执行最终检查。这样，验证结论就不会受到生成代码时所依据的假设的影响。

<div style="display: flex; gap: 16px; margin-top: 1rem;">
  <div style="flex: 1; background: #f5f5f5; padding: 16px; border-radius: 8px;">
    <strong>传统模式</strong>
    <p style="font-size: 14px; margin-top: 8px;">证明代码能够正常工作的信号来得很晚；几分钟之后CI才会报告问题，几天后测试人员才会发现问题，甚至几周后到了生产环境才暴露问题。当代码由智能体生成时，反馈来得太晚，就意味着必须由人工检查智能体的全部产出，而这个人也因此成为整个流程的瓶颈。</p>
  </div>
  <div style="flex: 1; background: #fff0eb; padding: 16px; border-radius: 8px;">
    <strong>AI 原生模式</strong>
    <p style="font-size: 14px; margin-top: 8px;">在人工查看执勤啊，会话已经具备检查自身工作的方式：运行测试、执行构建、生成截图。Claude会持续迭代，直到检查通过，因此交到工程师手中的结果已经完成验证。建立这一反馈闭环，是启动该会话的工程师需要负责的工作；下文将介绍具体做法。</p>
  </div>
</div>

**开始之前**

{{< info-list >}}

前置条件

: 无

基础设施

: 一套可以在本地运行的测试套件和构建流程，并且两者都能通过一条命令启动。对于UI工作，关键是让Claude能够看到测试结果，可以使用浏览工具或者通过MCP接入截图工具。

{{< /info-list >}}

**如何实施**

1. 如果当前检查工作需要依次执行多条命令，并且还需要了解一些环境配置，就将这些步骤封装成一个统一入口，例如make test或npm test。检查失败时，该命令应以非零状态码退出。
2. 在CLAUDE.md的Command部分列出每条命令，并为每条命令提供一份正常运行时的输出示例。
3. 明确任务目标，并将其转化为可衡量的标准，使Claude无需询问你便能自行检查工作。例如：“test_status.py中的所有测试均通过”、“截图与附带的设计稿一致”，或者“接口返回状态码200，并包含新增字段”。
4. 修复缺陷时，先编写一个能够失败的测试。让Claude用测试复现该缺陷，运行测试，并确认测试失败的原因符合预期。然后提交这个测试。滞后再要求Claude在不修改该测试的情况下修复代码，使测试通过，并使用最后一步介绍的测试文件Hook强制执行这一限制。一个在修复前就已经存在、而且智能体无法改写的测试，可以证明该缺陷确实已经消除。
5. 对于UI工作，应通过视觉检查完成反馈闭环。为Claude提供浏览器或截图工具以及设计稿，让它不断迭代：实现、截图、比较并调整。通过需要两到三轮，结果应当在每一轮中都有所改善。
6. 将验证纳入“完成”的定义，并把这项要求写入CLAUDE.md。在报告任务完成之前，必须运行测试并展示测试输出。
7. 最后，还需要保护反馈闭环本身，因为负责修复代码的智能体不能有能力削弱针对这些代码的检查。可以通过Hook阻止智能体在修复任务期间编辑测试文件。另一种做法是在代码审查时检查差异，并拒绝任何涉及测试文件的修改。

**示例内容（CLAUDE.md中的验证部分）**

```markdown
## 验证你的工作

- 构建：make build（必须以“Build succeeded”结束）
- 测试：make test （所有测试必须通过；绝不能跳过或删除失败的测试）
- 代码检查：make lint（不得出现警告）

在报告任何任务完成之前，先运行以上三项检查，并粘贴相应的输出。如果测试失败，应修改代码，而不是修改测试。
```

**治理考量**

{{< info-list >}}

强制执行的内容

: 在任务被报告为完成之前必须进行验证；在修复缺陷期间，禁止智能体编辑测试文件。如果组织希望确保这些要求得到执行，可以通过Hook实现这两项限制。

验证依据

: Claude实际运行并粘贴的make test输出、构建日志和截图差异。这样，验证依据直接来自工具链。

记录位置

: 这些信息记录在会话日志中，并由OpenTelemetry导出到组织的可观测平台；同时也记录在PR的检查结果中，方便审查人员查看，也便于审计人员日后审阅。

批准人员

: 由负责审查PR的代码负责人批准。由于相关的自动化验证结果已经附在PR中，代码负责人可以将注意力集中在修改意图和潜在风险上。

{{< /info-list >}}

**如何衡量效果**

{{< info-list >}} 

先行指标

: 智能体编写的代码变更首次通过CI的比例。现有的CI系统通常已经能够提供这一指标。

滞后指标

: 每个PR的审查时间，可以从PR元数据中获取。当测试能够发现过去需要审查人员才能发现的问题后，该指标应当下降；此外，应关注从事故追踪系统中获取的变更失败率。

{{< /info-list >}}



{{< lead >}}

在CI中持续进行评估

{{< /lead >}}

评估（Evals）相当于AI原生开发中的阶段关卡式质量保证。在实践中，这意味着每当智能体的配置发生变化时，都要运行一套评估用例。当更换新模型或重写提示词时，评估套件会判断智能体能否继续按照相同标准完成工作。

评估套件应被视为一套持续更新的测试集合。随着模型能力的提升，过去能够区分模型表现的用例可能不再有效，因此需要根据持续监控中发现的新问题，不断加入新的评估用例。

根据具体的使用场景，有些团队可能更愿意按照固定周期离线运行这些评估，而不是在每次变更时都运行。下面介绍的是持续评估的实施方式。

**开始之前**

{{< info-list >}}

前置条件

: 需要准备CLAUDE.md，并建立反馈闭环（**阶段4：测试**）。

基础设施

: 需要一个能够以非交互方式运行Claude Code的CI环境，以及一个配有评估运行预算的API密钥。

{{< /info-list >}}

**如何实施**

1. 平台工程师从近期工作中收集20~30个真实任务，并为每项任务记录预期或已认可的结果。
2. 将每项任务编写成一个评估用例，也就是为任务准备提示词，以及用于判断结果是否可以接受的检查标准，例如：测试通过、代码检查无问题、原有行为保持不变、相关策略得到遵守。
3. 评估套件按照计划在CI中以非交互方式运行；每当CLAUDE.md、Skill或Hook发生变化时，也要运行这套评估。因为这些配置会引导智能体的行为，所以它们应当接受与代码相同的回归测试。
4. 根据评估结果对配置变更设置合并门槛。如果某项Skill的修改导致通过率下降，就必须先接受审查，确认没有问题后才能合并。
5. 每次生产环境事故都应转化为一个评估用例，由负责处理该事故的团队编写，并作为回归测试长期保留在评估套件中。

示例配置（.github/workflows/agent-evals.yml）

```yaml
name: Agent评估

on: 
	pull_request:
		paths: ['CLAUDE.md', '.claude/**']
	schedule:
		- cron: '0 2 * * *'

jobs:
	evals:
		runs-on: ubuntu-latest
		steps:
				- uses: actions/checkout@v4
				- run: npm install -g @anthropic-ai/claude-code
				- name: 运行评估套件
					env: 
						ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          run: |
          	for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' "$eval")" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
            done
```

**治理考量**

评估机制为质量保证提供了一道能够跟上智能体产出速度的关卡。评估通过率的最低要求会作为合并检查强制执行；每次运行都会记录结果，以便比较一段时间内的变化；对相关配置负责的团队则负责批准这些变更。

**如何衡量效果**

{{< info-list >}}

先行指标

: 评估套件每次运行时报告的通过率变化趋势，以及一次生产环境事故被转化为永久评估用例所需的时间。

滞后指标

: 比较CI中发现的回归问题与生产环境中发现的回归问题。生产环境中的回归问题数据来自事故追踪系统。

{{< /info-list >}}

## （七）阶段五: 部署

审查是双向的，治理要求会在智能体执行操作的过程中得到强制落实。智能体可以完成生产环境关卡之前的所有工作，但不能越过这道关卡。

### 将AI纳入PR审查闭环

{{< lead >}}

Claude既可以审查他人的代码，也可以接受他们对其代码的审查。它会根据组织的策略审查新提交的PR，也会处理自己所提交PR中收到的审查意见。这样，工程师就能把注意力集中在PR所体现的行为上，重点判断修改意图是否正确，以及相关风险是否可以接受。

{{< /lead >}}

<div style="display: flex; gap: 16px; margin-top: 1rem;">
  <div style="flex: 1; background: #f5f5f5; padding: 16px; border-radius: 8px;">
    <strong>传统模式</strong>
    <p style="font-size: 14px; margin-top: 8px;">代码审查能力是按照人工产出规模来规划的。每个PR都需要等待审查人员逐行阅读；审查质量会随着审查人员的工作负荷而变化，而随着待审查任务不断积压，PR作者还需要持续催促审查进度。</p>
  </div>
  <div style="flex: 1; background: #fff0eb; padding: 16px; border-radius: 8px;">
    <strong>AI 原生模式</strong>
    <p style="font-size: 14px; margin-top: 8px;">所有PR都会经过一套相同的审查流程，并按照严重程度排列发现的问题。人工审查提升到更高层次，重点判断代码变更是否实现了计划中的意图，以及相关风险是否可以接受。</p>
  </div>
</div>

**开始之前**

{{< info-list >}}

前置条件

: 需要准备**阶段3: 构建**中更新过的CLAUDE.md；如果审查流程需要执行书面策略，还应准备相应的Skill；同时还需要定义好相关的子智能体。

基础设施

: 需要一个已安装Claude集成的代码仓库。可以选择以下任一种方式：由管理员启用托管式Code Review服务（研究预览版）；在自己的CI环境中运行claude-code-action。如有需要，模型调用还可以调用AWC Bedrock、Google Vertex AI或Microsoft Foundry完成，具体方式可参考CI/CD实施指南中的部署选项。此外，设置要求代码负责人批准的分支保护策略也很有价值。

{{< /info-list >}}

**如何实施**

1. 托管式Code Review服务是最快的入门方式。管理员启用该服务并选择要接入的代码仓库。如果需要自行控制流水线，或者希望API调用通过组织自己的云服务协议完成，可以使用claude-code-action在自己的CI环境中运行审查流程（具体配置方式可参考CI/CD实施指南）。
2. 技术负责人在代码仓库根目录编写REVIEW.md，将审查策略划分为组织关注的几个方面：程序缺陷和逻辑错误；安全问题和漏洞；是否符合规格说明（需求阶段生成的spec.md）；是否符合实施计划（规划模式生成的plan.md），以及是否遵循设计原则。REVIEW.md还应定义哪些问题属于重要问题，哪些只是细节建议，并明确哪些内容可以跳过。
3. 技术负责人设定需要人工介入的标准。审查发现的问题本身不会自动批准或阻止PR，分支保护策略仍然要求由代码负责人进行批准。如果平台工程师希望根据审查结果决定是否允许合并，可以读取检查任务所发布的严重程度统计；该统计采用机器可读的格式。
4. 当审查人员或PR作者在审查评论中标记@claude时，Claude会处理该评论并提交修复。PR的讨论记录中会同时保留修改请求和相应的代码变更。这一修复闭环通过claude-code-action运行。在托管式服务中，可以通过评论@claude review请求重新审查。对于由Claude创建的PR，团队还可以进一步让Claude持续跟进该PR，直至满足合并条件。团队可以将整个流程封装成一个自定义斜杠命令: 检查PR中尚未解决的审查意见和未通过的检查，逐项处理并推送修复，直到PR的所有检查均已通过，只等待代码负责人批准。
5. 将审查发现的问题反馈到CLAUDE.md。当审查人员第二次发现同一种错误时，就应在审查过程中把相应的纠正说明写入CLAUDE.md。由于后续审查会读取该文件，从下一个PR开始，这类错误就能够被提前发现。审查流程还应指出哪些代码变更已经导致CLAUDE.md中的内容过时。
6. 技术负责人每月调整一次审查设置: 通过评价审查结果，持续改进审查器；同时在REVIEW.md中限制细节建议Nit的数量。自动生成的文件路径，以及已经由CI强制检查的内容，都应从审查范围中排除。

**示例内容（REVIEW.md）**

```markdown
# 审查说明

## 审查轮次
执行三轮审查，并表明每个问题是在哪一轮审查中发现的:
- 缺陷Bugs: 逻辑错误、失效的边界情况、难以觉察的回归问题
- 安全Security: 注入风险、身份验证缺失、日志中出现个人身份信息（PII）
- 合规Compliance: 确认代码变更符合spec.md、plan.md和我们的设计原则。

## 重要问题的定义
只有可能破坏系统行为、造成数据泄漏或违反策略的问题。才能标记为“重要问题”。代码风格和命名问题属于细节建议。

## 限制细节建议的数量
每次审查最多报告五条细节建议，其余问题只需汇总数量。

## 不要报告以下内容
src/gen/目录下的自动生成文件，以及CI已经强制检查的内容。
```

**治理考量**

职责分离任然得到保留，因为编写代码的智能体无法批准自己的代码。REVIEW.md中的审查策略适用于所有的PR；审查中发现的问题、修复内容、评价和批准记录都会保留在PR历史中，因此PR本身就是审计记录。最终批准仍由人工通过分支保护机制完成，而审查结果会为人工决策提供依据。

{{< lead >}}

将Hook用作审批关卡

{{< /lead >}}

在构建阶段，Hook被用作防护机制，无需人工介入即可允许或阻止某项操作（阶段3：构建）。Hook也可以发起审批请求，并暂停当前操作指导指定人员批准；这正是发布关卡所需要的机制。

这一做法被放在**阶段5：部署**中进行介绍，是因为发布关卡是最典型的应用场景。不过，Hook并不只用于部署：只要Claude执行操作，Hook就可以运行。例如，在**阶段3:构建**中，Hook可以阻止在没有变更工单的情况下修改数据迁移和基础设施；在**阶段4：测试**中，Hook可以阻止智能体在缺陷修复任务期间编辑测试文件。

{{< info-list >}}

前置条件

: 无

基础设施

: 一份书面清单，列明变更流程要求经过哪些审批。

**如何实施**

1. 工程管理层与变更管理和合规团队共同列出必须保留的人工审批关卡，例如变更管理签核、发布授权，以及对受保护路径的修改审批。
2. 平台工程师奖每一道关卡实现为Hook，也就是在Claude执行操作之前运行的脚本。该脚本可以允许操作、请求批准或阻止操作。
3. 团队级Hook应存放在.claude/settings.json中，并提交到Git。不可取消的Hook则应放入由平台管理员或IT管理员维护的托管设置中，使普通工程师无法将其关闭。
4. 阻止操作时应当说明原因。因此，当Hook中止某项操作时，Claude的输出中应显示阻止原因，以及获得批准的途径。

**示例配置（.claude/settings.json）**

```json
{
  "hooks": {
  "PreToolUse": [
    {
      "matcher": "Bash",
      "hooks": [
        { "type": "command",
        	"command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/production-gate.sh"}
      	]
			}
    ]
	}
}
```

审批关卡脚本（.claude/hooks/production-gate.sh）

```bash
#!/bin/bash

# 部署到生产环境中必须具有明确指定的发布授权
cmd=$(jq -r '.tool_input.command' < /dev/stdin)

if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
	if [ -z "$RELEASE_APPROVAL" ]; then
	echo "Production deploys need a release authorization." >&2
	exit 2 # exit 2 blocks the action; the message goes to Claude
	fi
fi

exit 0
```

**治理考量**

Hook就是审批关卡。无论由谁执行操作，每次都会强制检查关卡条件。允许或阻止操作的决定都会与时间戳一起记录下来。审批关卡还需要明确什么情况下才算获得批准，例如已经审批的变更工单，或者发布经理的正式签核。

{{< worked-example label="实践示例（续）" title="从控制角度看，每项配置分别带来了什么" >}}

**permissions.deny**与**permissions.allow**

**permissions.deny**可以防止敏感信息进入智能体的上下文，同时阻止工具随意向外部网络发送请求；permissions.allow则预先批准安全的日常操作，避免拒绝列表导致频繁弹出授权提示，使用户产生审批疲劳。

**disableBypassPermissionsMode**与**allowManagePermissionRulesOnly**

这两个配置结合使用后，无论是工程师、项目配置文件，还是命令行参数，都无法放宽阻止设定的权限规则。

**sandbox**

**sandbox**可以弥补权限规则无法覆盖的安全缺口。仅在工具层面禁止WebFetch，并不能阻止Shell命令访问网络；而操作系统层面的域名允许列表可以直接阻止未经允许的网络连接。

**failIFUnavailable**和**allowUnsandboxedCommands**会让沙箱成为一道强制关卡：当沙箱无法初始化时，Claude Code会拒绝启动；如果某条命令在沙箱内执行失败，也不能转到沙箱外重新执行。

**credentials**

**credentials**可以弥补拒绝规则留下的凭据保护的缺口。**permissions.deny**主要约束Claude的文件工具，但在默认情况下，沙箱中的Shell命令仍有可能读取`~/.ssh`或`~/.aws/credentials`。该配置会禁止读取这些文件，并且从每条沙箱命令的环境变量中移除指定的敏感信息。

**allowManageHooksOnly**

该配置意味着只有本方案中由组织统一管理的审批Hook可以运行；本地配置无法增加新的Hook，也无法替换现有Hook。

**disableSideloadFlags**与**strictKnownMarketplaces**

这两个配置结合使用后，工程师计算机上的所有Skill、Agent、Hook和MCP Server都必须来自组织批准的插件市场，而不能从个人主目录等本地位置加载。

**allowManagedMcpServersOnly**

该配置将智能体可以使用的工具限制为一份由平台团队统一管理的允许列表。

**requireMinimumVersion**

如果当前Claude Code版本低于组织批准的最低版本，系统将拒绝启动。这样可以确保相关控制措施由组织已经评估过的版本负责执行。

以上配置应当作为定制设置的起点，而不是可以直接照搬的推荐方案。每项拒绝规则都会以牺牲部分性能为代价，具体如何平衡，应根据代码仓库中的数据分类情况决定。设置参考文档列出了所有配置项，包括仅支持托管设置的选项：[Claude设置文档](code.claude.com/docs/en/settings)

前置条件

基础设施

: 一个安装了claude-code-action的CI平台，或任何能够运行claude -p的执行器；通过API访问模型；如果调用流量必须遵循组织的云服务协议，则通过Bedrock、Foundry或Vertex访问。面向部署目标的MCP Server；为智能体任务配置的沙箱策略，且不提供长期有效的生产环境凭据。

**如何实施**

1. 平台工程师先从只读的判断任务入手。在流水线任务中使用claude -p，分析构建失败的原因、总结不稳定测试的情况，或起草变更日志。
2. 在现有审批关卡的约束下，加入需要写入操作的步骤，例如修复代码检查问题、更新自动生成的文档，或者处理通过@claude提及的审查意见。智能体编写的任何修改都必须通过PR提交，并接受分支保护规则的约束；智能体不能直接向main分支推送代码。
3. 在沙箱中执行任务。智能体任务运行在受网络约束的容器中，使用有效期短、权限范围受限的令牌，并且默认不持有生产环境凭据。
4. 通过MCP提供部署能力。将部署、状态查询和回滚封装成工具，并分别限定其可操作的环境。这样，智能体的部署权限就由明确的允许列表控制，而不是依赖一个持有凭证的Shell脚本。
5. 按环境设置不同程度的自主权限。在开发环境中，智能体可以自主部署；在生产环境中，智能体负责准备发布，由发布经理授权，并通过Hook强制执行生产环境关卡。预发布环境的自主权限则介于两者之间。
6. 回滚应当是流水线中演练最充分的流程。回滚应当是流水线中演练最充分的流程。将其封装成智能体可以执行的一条命令，并定期在预发布环境中演练。在闭环流程（阶段6: 维护）中，一旦指标超出控制范围，就会调用这一回滚操作，因此必须提前验证它确实有效。

示例配置（流水线步骤）

```markdown
- name: 分析构建失败
	if: failure()
	run: >
		claude -p “读取out/build.log中的构建日志。找出最可能的原因，说明这次失败看起来是偶发的不稳定问题，还是真实故障，并为PR讨论串撰写一份三行摘要。”>> triage.md
```

**治理考量**

核心原则是：智能体可以执行生成环境关卡之前的操作，但不能越过这道关卡。以下控制措施用于强制落实这一原则。

+ 分支保护要求智能体编写的任何修改都必须通过PR提交，不能直接进入main主枝。
+ 生产环境部署Hook会阻止发布，直到指定的发布经理授权。每次非交互式运行都适用智能体自身的身份，因此流水线日志能够区分哪些操作由智能体执行，哪些操作由触发该任务的工程师执行。
+ 针对不同环境设置的权限等级，决定了智能体在到达关卡之前可以执行哪些操作。

根据 CI/CD 流水线日志统计，在无需人工介入（即无需向人员发送告警）的情况下完成处理的流水线故障所占比例。

## （八）阶段六：维护

至此形成完整闭环。触发机制会自动调用claude，无需人工介入调用过程；Claude发现的问题则以intent.md的形式重新进入流水线。

### 维护与形成闭环

{{< lead >}}
到目前为止，我们讨论了如何将Claude引入软件开发生命周期（SDLC）的各个阶段，但每个阶段仍需要人工启动最初的步骤，而这一阶段的重点，则转向让Claude自主运行，从而形成闭环。
{{< /lead >}}

例如，一次持续运行的监控智能体，可以在收到新建的缺陷工单后创建intent.md，然后一次推进需求、规划、构建、测试和审查阶段。“**阶段6:维护**”以无需交互的方式运行，并在各阶段之间设置独立的置信度关卡：通过确定性检查或对抗式审查智能体，判断上一阶段的产出应继续进入下一阶段，还是交由人工处理。

**如何实施**
1. 选择一个具有稳定滚动极限的指标。由服务负责人或平台工程师选定，例如CI测试失败率、部署后的5xx错误率，或者PR周期时长。
2. 编写监测脚本。通常基于滚动时间窗口计算均值和标准差，并结合判定规则（例如Western Electric规则或者类似规则），让控制区间既能识别缓慢漂移，也能捕捉突然出现的尖峰。脚本应纳入版本控制并经过单元测试；整个监测过程保持完整确定性，不涉及模型。
3. 在纳入版本控制的配置中定义响应级别。具体参见下方的bands.ymal，达到1$\sigma$时，脚本只记录日志；达到2$\sigma$时，调用Claude，以只读方式诊断问题。达到3$\sigma$时，允许Claude采取行动，但仅限于创建PR、进入审查关卡，或者触发预先批准的操作手册流程（runbook）。
4. 设置触发机制。触发层可以是GitHub或GitLab中的定时工作流、现有监控系统发出的webhook，或者内部网络中的Cron定时任务。Claude以无状态方式运行，可以作为CI执行器上的非交互步骤，也可以作为沙箱容器中的Agent SDK服务。CI/CD章节介绍了部署方式和模型接入选项。由于运行过程是无状态、非交互的，整个闭环无需人工启动，就能自行开始并完成。
5. 将诊断结果写入`intent.md`。智能体按照**“阶段1：规划”**中的格式，将诊断结果写入`intent.md`，涵盖异常及其证据、建议达成的结果、受影响的系统，以及尚待澄清的问题。之后，这些发现便像其他任务一样进入后续流水线。
6. 由人工对待处理事项进行分流。服务负责人或值班工程师对队列中的事项进行分类处理，将涉及的产品发现转交给产品负责人，并决定立即修复、安排后续处理或者忽略。被忽略的事项可用于调整控制区间，帮助减少告警噪声。
7. 修复上线后，为该事故添加评估用例。按照“持续评估”章节的方法，为此次事故新增一个评估用例，确保今后能够防范此类问题。

**配置示例（以下是一个用于监控CI测试失败率的`bands.yaml`示例）**
```yaml
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read, Grep, Bash(gh run view *)" }
  3sigma: { action: propose,
            tools: [pull_request, runbook: rollback-deploy] }
```

**治理考量**
各响应级别的边界由纳入版本控制的配置强制执行，同时通过权限和托管设置禁止智能体访问生产环境。每次调用、发现的问题以及分流决策，都会连同时间戳一起记录。服务负责人负责对发现的问题进行分类处理和审批；由此产生的变更仍须经过常规的PR审查关卡；智能体能够触发的操作手册流程，也必须事先获得批准。

**如何衡量效果**
{{ info-list }}
领先指标
: 从指标超出控制区间，到生成的`intent.md`进入待分流队列所需的时间，并与以往从事故发生到启动事后复盘改进行动所需的时间进行比较。检测脚本的日志中记录了越界时间戳与对应的事件级别。
滞后指标
: 发现的问题中，最终转化为已合并修复的比例（通过对照待分流队列与实际PR历史记录计算），以及同类事故的重复发生次数。随着修复过程中不断向评估套件补充用例，同类事故的重复发生次数应逐渐下降。
{{ /info-list }}

**示例**
+ 当CI测试失败率突破3$\sigma$控制界限时，智能体会隔离不稳定的测试，或者创建一个回退变更的PR，再由审查关卡决定是否接受。
+ 当部署后的**5xx错误率突破3$\sigma$**控制界限，且监测时间窗口内确实发生过部署时，智能体会触发现有的回滚流水线。
+ 当PR周期时长触发漂移判定规则时，智能体会为工程管理层撰写一份报告。这表明，这套运行与管控框架不仅适用于生产环境指标，也适用于流程指标。
> 检测过程始终保持确定性。只有在指标超出控制区间后才会调用Claude；响应级别决定了它可以执行哪些操作。

### 通过 Claude Tag 参与值班响应
事故也可能通过其他渠道传来，例如Slack或Teams等工作沟通应用。比如，晚上10点，事故频道里出现了一条要求紧急修复的Slack消息，现在就可以立即响应。Claude Tag（原文所述公开测试版目前支持Slack）让Claude以独立身份成为这些频道的成员，使每一起新事故都能得到第一时间响应，而响应过程本身也会成为闭环的一部分，并为未来的事故处理积累记忆。
讨论内容和组织积累的知识都保留在频道中，频道里的任何成员都可以引导响应过程并推动处理。团队成员可以实时验证假设、探索其他方案并展开调查，而频道历史记录则增强了整个过程的可审计性。Claude通过MCP接入相关工具，验证指标是否已经恢复到基线水平，并在讨论串中确认；随后，将事后复盘写入纳入版本控制的经验教训文件，供未来的调查查阅。Claude Tag接手的工作不只有事故。无论是通过MCP在工单中标记Claude，还是直接在频道里向它提出请求，Claude都会以同样的方式对任务进行分类处理。范围较小、边界明确的修复会以PR的形式进入审查关卡；规模更大的任务则会被整理成intent.md，交给“阶段 1：规划”处理。至此，闭环开始自行产生下一轮工作的输入。
